# Frontend type-contract migration audit

## Scope

This audit records the phase-1 migration from ambient JSDoc contracts to
module-scoped declarations. It covers catalog schema generation, canonical-only
input boundaries, the TypeScript 7 type gate, and the original
runtime-neutral migration proof.

## Contract ownership

- `schemas/catalogs.generated.schema.json` is the source of truth for the
  canonical public catalog model.
- `types/catalog-data.generated.d.ts` is generated by
  `tools/generate_catalog_data_types.py`.
- Catalog source files, control-panel payloads and browser runtime data accept
  only the canonical field names declared by their JSON Schemas. Compatibility
  aliases were removed rather than retained as a second input model.
- `types/frontend-contracts.d.ts` owns module-scoped UI/application contracts.
- `types/frontend-globals.d.ts` contains only intentional browser/platform
  augmentations and build-provided globals.
- `src/js/05-app-contracts.js` declares no types and remains only as a stable
  source-inventory marker.

## Compatibility gates

The canonical frontend JSDoc configuration is checked by both compilers:

- TypeScript 7.0.2 (`node_modules/typescript`)

The temporary TypeScript 5.8 compatibility lane was retired after the TypeScript 7 migration closed. The type gate, AST inventory, runtime-symbol checker and offline bootstrap now share TypeScript 7 as their only compiler contract.

Both compilers are installed from package-lock-pinned, SHA-512-verified local
archives. `tools/verify_project.py` also rejects stale generated catalog
contracts before running the matrix.

## Canonical-only closeout

The follow-up closeout removed the compatibility boundary completely:

- no legacy catalog declaration file remains;
- the browser groups catalogs only by `CatalogRecord.subcategory`;
- taxonomy and control-panel tools read and write only `subcategory`;
- `catalogs.config.json` is schema-validated when read and immediately before
  persistence; and
- contract tests reject reintroduction of non-canonical aliases.

This intentionally changes behavior only for invalid, pre-schema catalog
objects. Current canonical catalog data and generated public output retain the
same meaning and ordering.

### Runtime delta for canonical-only closeout

The closeout intentionally removes executable compatibility logic, so the three
routes that included the former shared UI owner are no longer byte-identical to the
pre-closeout build. The builder diff was isolated to the body of
`catalogSubcategoryName` (now owned by `20-catalog-runtime.js`); all other generated assets stayed byte-identical.
